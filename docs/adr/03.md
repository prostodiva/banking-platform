# ADR-003: Transfers — cross-context calls, atomicity, and idempotency

Date: 2026-08-19
Status: Accepted

## Context

Slice 4 (FR-PAY-01, `POST /api/payments/transfers`) is the first slice that
spans two bounded contexts. It raises three questions slices 1–3 never did:

1. **How does `payments` move money that `accounts` owns?** `ArchitectureTest`
   forbids `payments` from importing anything in `accounts`, and the rules that
   guard a balance (`Account.withdraw`, `Account.deposit`) live in the accounts
   aggregate. Payments must reach them without reimplementing them and without
   importing them.
2. **What is atomic?** A transfer is a debit and a credit. Half a transfer is
   money destroyed or invented.
3. **What happens when the client retries?** A transfer request that times out
   is ambiguous to the caller — the money may or may not have moved. Their only
   safe recovery is to send it again, so the endpoint has to make that harmless.
   Deposit and withdraw ducked this: they are called by a human looking at a
   screen, transfers will be called by machines. See
   [docs/12](../12-open-questions.md) for the framing this ADR closes.

## Decisions

### 1. Contexts talk through published application ports, not domain imports

`accounts` publishes one interface in `accounts/application/port/`:

```java
public interface AccountLedger {
    void moveMoney(UUID fromAccountId, UUID toAccountId, Money amount);
}
```

`payments` depends on that interface and on nothing else in `accounts`.
`Account`, `AccountRepository`, `AccountResponse` and every other type in the
context stay invisible to it. The implementation is an `@Service` in
`accounts/infrastructure/` that loads both aggregates and calls the existing
`withdraw` / `deposit` methods — the invariants stay in one place.

The port is named in **accounts' own vocabulary**, not payments'. Accounts
understands "move money between two of my accounts"; it does not know that the
caller wraps that in something called a Transfer with an idempotency key. Had
the method been `transfer(...)`, payments' vocabulary would have leaked across
the boundary, and the next consumer (a future refund, a fee sweep) would arrive
to find a method named after somebody else's use case.

The dependency arrow points `payments → accounts`, matching the roadmap's
ordering ([docs/23](../23-slice-roadmap.md)). Consumer-defined ports — payments
declaring the interface and accounts implementing it — would invert the arrow
and force `accounts` to import `payments`, which is worse: the upstream context
would then need recompiling every time a downstream one is added.

**Rejected: event choreography.** Publishing `TransferRequested` and having
accounts react is the right shape once payments is a separate service with its
own database. Today both contexts share one Postgres and one transaction, so
choreography would replace an atomic operation with a saga plus compensating
transactions — strictly more code, strictly weaker guarantees, in exchange for
decoupling that nothing currently needs. Events still carry the *outcome*
(decision 5); they just don't carry the *request*.

Switch trigger: the day payments owns a separate datastore, or a transfer leg
becomes a call to an external rail with its own latency. At that point the port
implementation becomes an event publisher and `Transfer` grows the status
machine deferred in decision 4.

### 2. `ArchitectureTest` gains a published-API rule

The current slice rule forbids **all** cross-context dependencies except onto
`shared`. That is stricter than [ADR-001](01.md), which said contexts
communicate "via domain events or application-service interfaces only" — the
test simply never encoded the second half. Slice 4 makes the gap load-bearing,
so the rule is amended to say what was always intended:

- a context may depend on another context's `application.port..` package;
- a context may **not** depend on another's `domain..`, `infrastructure..` or
  `api..` — this half is new, and is tighter than what the old rule expressed,
  because it now says so explicitly rather than as a side effect.

This is a deliberate change to the architecture, recorded here before the code
exists. It is not the thing [docs/23](../23-slice-roadmap.md) warns against —
relaxing a rule *because a slice won't compile*. The test is being brought in
line with an ADR that predates it, and the net rule set is stricter, not looser.

`application/port/` now holds two kinds of interface: outbound ports the context
calls (`DomainEventPublisher`) and inbound ports it publishes for others
(`AccountLedger`). The package's `package-info.java` states which is which.

Switch trigger: if a context ever publishes enough interfaces that the two kinds
get confused, split them into a dedicated `contract/` package per context and
point the ArchUnit rule at that instead.

### 3. One transaction, ordered locks, existing optimistic locking

`TransferMoneyHandler` is `@Transactional`; `moveMoney` joins that transaction
rather than starting its own. Both legs commit or neither does. No saga, no
outbox, no two-phase anything — one database makes this a solved problem, and
pretending otherwise would be cargo cult.

`moveMoney` sorts the two account ids before loading them, so concurrent A→B and
B→A transfers always take row locks in the same order. Unordered access is the
textbook deadlock, and it only shows up under load, which is exactly when you
cannot debug it.

`@Version` on `Account` (ADR-002) already covers lost updates and needs no
change. What it does need is an HTTP mapping: `OptimisticLockingFailureException`
is currently unmapped and would surface as a 500. It maps to **409** — the
request was well-formed and the caller may retry.

### 4. `Transfer` is a completed record, not a state machine

The aggregate stores `id`, `fromAccountId`, `toAccountId`, `Money amount`,
`idempotencyKey`, `createdAt`. There is no `status` column and no
`PENDING`/`FAILED` enum. In a single synchronous transaction a transfer either
committed — in which case the row exists and it succeeded — or it rolled back,
in which case the row does not exist. A status field with one reachable value
documents a design that isn't there.

Cross-context references stay by id: `Transfer` holds account **UUIDs**, never
`Account` objects, and there is no FK to `accounts` — the two tables belong to
different contexts and would be in different databases after an extraction.

Switch trigger: the moment a transfer can be in flight across a process boundary
(decision 1's switch trigger), status appears along with it.

Consequence to accept: a **failed** transfer leaves no trace. "Show me my
declined transfers" is unanswerable. When that requirement arrives it needs a
separate append-only attempt log written in its own transaction
(`REQUIRES_NEW`), not a status column on the rolled-back row.

### 5. One business fact, one event

`TransferMoneyHandler` publishes `PaymentCompleted` (payments context) after
save, inside the transaction, through the existing `DomainEventPublisher` port —
same convention as every other handler ([docs/06](../06-event-model.md)).

`moveMoney` publishes **nothing**. Reusing the deposit/withdraw handlers would
have fired `MoneyWithdrawn` and `MoneyDeposited` as well, and the notifications
slice would then tell one customer three things about one transfer. Downstream
consumers that need per-account statement lines derive both legs from
`PaymentCompleted`, which carries `transferId` alongside both account ids and
the amount — without the id a consumer can name the accounts but not the payment
it is reacting to.

**A replay publishes nothing.** The event marks the transfer *happening*, and a
replayed request is not a second happening — it is the same one being reported
again. Publishing on the replay path would mean a client retrying five times
produces one transfer and five events, and the fraud slice would see five
payments where the ledger has one. The publish therefore lives on the insert
path only; the replay path (decision 6) returns the stored response and stops.

### 6. Idempotency: client-supplied key, unique index, replayed response

**The key comes from the client**, in a required `Idempotency-Key` header
(Stripe's model). A missing key is a 400. Deriving the key server-side from
`(from, to, amount, window)` would need no client cooperation, but it cannot
tell a retry from a customer genuinely sending $20 twice in a minute — and only
the caller knows which one it is. Guessing costs somebody $20 in one direction
or the other.

**The key is a column on `transfers` with a unique index**, not a separate
`idempotency_keys` table. The transfer row is written in the same transaction,
so one write covers both, and it carries the original request fields for free
(decision 7). A separate table would earn its keep only when requests that never
produced a transfer row still need protecting — which is exactly the failed-attempt
case deferred in decision 4, and arrives with it if it arrives.

**The unique index is the enforcement point, not an application-level check.**
Read-then-insert races itself under precisely the concurrent-duplicate case it
exists to prevent. `DataIntegrityViolationException` already maps to 409
([docs/11](../11-development-conventions.md)), so the collision surfaces with no
new plumbing — but for a replayed key the handler catches it rather than letting
it become the response.

**A replay returns the original response with its original status** — 201 and
the original `TransferResponse`, not a 409. Replaying the original is the entire
point: it is what lets a client retry blindly until it gets an answer. A 409
would force every caller to implement a second "go find out what actually
happened" path, which is the ambiguity this decision exists to remove.

Flow: read by key first (the common replay case, one indexed lookup) — if a row
exists, compare bodies (decision 7) and return the stored response **without
inserting, without moving money and without publishing** (decision 5). Otherwise
insert, move the money, publish, and return 201; on unique violation re-read by
key and take the same replay path. The fast path is a read, the index is the
backstop, and the race resolves to the same answer either way. A duplicate that
arrives while the first is still in flight blocks on the index until the first
commits, then replays it — Postgres gives that behaviour for free.

The key is a client-chosen opaque **string** (`varchar(64)`), not a UUID.
Constraining the format would reject keys a correct client is entitled to send;
the only thing this system needs from a key is that it is stable across retries
and unlikely to collide, and both are the client's job.

Idempotency stays a `payments` concern. Deposit and withdraw stay unprotected
because a human clicking a button owns the ambiguity themselves — they can look
at the balance. Switch trigger: the day either endpoint is called by a machine,
or the day payments is extracted and can no longer share this transaction,
`accounts` needs its own key. It goes on an append-only `account_entries` table
— one row per movement, which is the thing a key identifies — and **never as a
column on `accounts`**, whose rows are entities, not requests.

### 7. Same key, different body → 422

The stored transfer row holds `fromAccountId`, `toAccountId` and `amount`, so a
replay is compared field by field against it. No request-hash column is needed.

A mismatch means a client bug — key reuse across genuinely different requests —
and returning the first result would hide it while quietly not performing the
second transfer. 422 says the request was understood and refused.

Keys are globally unique for now because there is no authenticated caller to
scope them to. When slice 5 lands, the constraint becomes
`(clientId, idempotencyKey)`, which is the correct scope: two customers must be
able to pick the same key. Until then, one careless client can burn a key for
everyone — accepted while the only clients are tests and the developer.

Keys are kept for the life of the transfer row, i.e. forever. Transfers are
permanent financial records, so there is nothing to expire; a retention policy
would only matter for the separate-table design that decision 6 rejected.

## Consequences

- Payments never sees an `Account`. Extracting it into its own service means
  replacing one interface implementation, not unpicking imports.
- The invariants that protect a balance stay in exactly one class. A transfer
  from a frozen account is refused by the same code path that refuses a
  withdrawal from one, and gets the same 409.
- `ArchitectureTest` now expresses the whole of ADR-001's boundary rule instead
  of half of it, and mechanically forbids the imports that would make the
  extraction above expensive.
- Every documented error on the transfer endpoint has a source:
  404 unknown account, 409 insufficient funds / non-active account, 400
  currency mismatch, 400 same-account transfer, 400 non-positive amount,
  400 missing `Idempotency-Key`, 409 concurrent modification,
  422 idempotency-key conflict.
- A transfer is a created resource: **201 + `Location`**, answered by
  `GET /api/payments/transfers/{id}` (FR-PAY-02). The read endpoint is not
  optional garnish — a `Location` pointing at a 404 is worse than no `Location`,
  and a permanent financial record the API cannot show back is odd on its own
  terms.
- Cross-currency transfers are refused with 400 by `Money.requireSameCurrency`.
  There is no FX in this project; the refusal is the feature.
- Failed transfers are invisible (decision 4), and a shared idempotency-key
  namespace is trusting (decision 7). Both are accepted deliberately and both
  have a named trigger for revisiting.
