# ADR-002: Persistence — Flyway migrations, JPA on the aggregate, Testcontainers

Date: 2026-07-27
Status: Accepted

## Context

Slice 1 (accounts/OpenAccount) introduces the database. Decisions needed on who
owns the schema, how the domain model maps to tables, and how persistence is
tested. This is a banking domain: schema changes must be auditable, money must
be exact, and concurrent updates must never be silently lost.

## Decisions

1. **Flyway owns the schema; Hibernate validates.** Versioned SQL migrations in
   `db/migration/` with `spring.jpa.hibernate.ddl-auto=validate`. Auto-DDL
   (`update`/`create`) is never used — schema history is code-reviewed and
   auditable. Applied migrations are immutable; fixes are new migrations.
   Dev seed data (V3, dev user) currently lives in the same folder — a prod
   profile would exclude it; accepted while there is no prod deployment.
2. **The aggregate is the JPA entity** (`Account` carries the mapping
   annotations), rather than a separate persistence model + mapper. Grounds:
   - It is the dominant practice in production Spring systems, including
     Spring Modulith's reference approach for modular monoliths — and realism
     is an explicit goal of this project.
   - It uses Hibernate as designed: handlers work with *managed* entities, so
     dirty checking and `@Version` optimistic locking work naturally. The
     separate-model pattern works with *detached* objects instead — every save
     becomes a `merge`, dirty checking is lost, and the optimistic-lock version
     must be hand-carried through the "pure" domain object, reintroducing an
     infrastructure field into the very model the pattern tries to purify.
   - The boundary that actually matters — *no framework behavior in domain* —
     is enforced mechanically by an ArchUnit test (`ArchitectureTest`, see
     docs/13 stage 6): no `org.springframework.*` dependencies and no
     outer-layer dependencies from `..domain..`. JPA annotations are inert
     metadata and remain permitted.
   - The known deformation risks of annotated entities are countered in the
     model's own design: no setters, private constructor + static factory,
     self-assigned UUIDs, DTOs at the API boundary, cross-context references
     by id.

   Switch triggers — introduce a separate persistence model *per slice* (the
   ports make this non-breaking) the day persistence shape diverges from the
   model: a legacy schema we don't control, event sourcing, or one aggregate
   spread across multiple stores.
3. **Money as an exact value.** `numeric(19,4)` columns + `BigDecimal` in an
   `@Embeddable Money` record. Floating point is banned for amounts.
4. **Optimistic locking from day one.** Every aggregate table carries `version
   bigint` + `@Version`. Lost updates fail loudly instead of corrupting balances.
5. **Enums stored as names** (`@Enumerated(EnumType.STRING)`, varchar columns) —
   reordering Java enums must never change stored meaning.
6. **Tests run against real Postgres via Testcontainers 2.x** with Boot's
   `@ServiceConnection`. H2 is banned: it validates against a different SQL
   dialect than production. The same Flyway migrations run in every test.

## Consequences

- Schema evolution is explicit and reviewable; startup fails fast when entity
  and schema drift apart.
- The domain stays unit-testable without Spring; only inert annotations tie it
  to JPA, and `ArchitectureTest` fails the build if framework behavior or
  outer-layer dependencies creep into `..domain..`.
- Test suite requires Docker; first run pays an image-download cost.
