# ADR-005: Notifications resolve account owners through an accounts query port

- **Status:** Proposed
- **Date:** 2026-11-11

## Context

`FraudAlertRaised` carries `fromAccountId` but no owner — the fraud context
keys its alerts on the account, and resolving account → owner was left as a
read/notification-side concern. Notifications cannot record a notification
without a recipient, so it must resolve the owner of `fromAccountId` across
the context boundary.

Options considered:

1. **Accounts-side query port** — notifications calls a published port on the
   accounts context (e.g. `AccountOwnershipQuery.ownerOf(accountId)`),
   following ADR-003: contexts interact through ports, never through each
   other's tables.
2. **Enrich the event** — add `ownerId` to `FraudAlertRaised` at the source.
   Rejected: it makes the fraud context responsible for a field it does not
   own or need, and every future consumer inherits whatever the producer
   happened to include.
3. **Direct table read** — notifications queries the accounts table.
   Rejected: cross-context table access breaks the bounded-context boundary
   every other context in this codebase respects.

## Decision

Option 1. Notifications resolves the recipient through an accounts-side
application query port. If the port does not exist yet, building it is part
of this slice.

## Consequences

- The `FraudAlertRaised` contract stays unchanged — no producer change, no
  redeploy of the fraud context.
- Notifications depends on the accounts context's published port at consume
  time. A failed or empty lookup follows FR-NOT-01: log and skip, never
  propagate.
- The same port is reusable by the planned owner-only authorization check on
  `GET /api/fraud-alerts/{accountId}`, which needs the identical lookup.
