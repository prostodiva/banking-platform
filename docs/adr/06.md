# ADR-006: Reports build their read model by projecting domain events

- **Status:** Proposed
- **Date:** 2026-11-23

## Context

Reports need a complete transaction history per account (FR-REP-01/02).
No such history exists as a table: transfers are persisted, but deposits
and withdrawals are not — they exist only as `MoneyDeposited` /
`MoneyWithdrawn` events. The accounts table holds only the current balance.

Options considered:

1. **Projection from events** — reports consumes `MoneyDeposited`,
   `MoneyWithdrawn` and `PaymentCompleted` and maintains its own
   `transaction_entries` read model (CQRS read side, docs/23 slice 8).
2. **Query the source tables** — union the transfers table with accounts
   data at read time. Rejected: deposits and withdrawals have no rows
   anywhere, so history would be silently incomplete.
3. **Synchronous ledger table** — accounts and payments write a shared
   ledger row inside their own transactions. Rejected: it changes two
   upstream contexts, duplicates facts the events already carry, and
   couples the write side to a read-side need.

## Decision

Option 1. Reports maintain a write-once projection, deduplicated on the
source id (`transferId` for transfers; a new `eventId` added to
`MoneyDeposited` / `MoneyWithdrawn` for account movements). Reports
publish no events and read no other context's tables; account ownership
is resolved through `AccountOwnershipQuery` (ADR-005).

## Consequences

- Reports are eventually consistent: a committed transaction appears
  within 5 seconds (NFR-REP-01), never before commit, exactly once.
- `MoneyDeposited` / `MoneyWithdrawn` gain an `eventId` field — a contract
  change in the accounts context, generated by the publishing handler.
- History starts when the projection starts: movements made before this
  slice have no entries and cannot be backfilled from events. Statements
  for pre-slice months will be incomplete.
