# ADR-004: Auth — token strategy, key custody, and privilege separation

Date: 2026-08-28
Status: Proposed

## Context

Slice 5 (FR-AUTH-01…04) adds the first identity to the system. Until now every
endpoint has been anonymous and `ownerId` has been a field the client sends,
which [docs/07](../07-authetication.md) names as the open IDOR in this codebase.

[docs/12](../12-open-questions.md) marks the signing algorithm as **"blocks
coding"**, and it does: HS256 and RS256 differ in what is stored, whether there
is a JWKS endpoint, and whether `kid` plumbing exists. Deciding it after tokens
are live means migrating tokens that are already in circulation.

Three further questions arrive with it, none of which slices 1–4 raised:

1. **Where does the signing key live**, in dev and in a deployment, given
   NFR-08 says signing keys get no default at all?
2. **What is a refresh token made of**, and what makes it revocable — the
   property that is its only reason to exist as a second token?
3. **How does an ADMIN come into existence** when the only endpoint that creates
   users is public? Registration that can produce an admin is a privilege
   escalation endpoint, and the role is the most attacker-attractive field in
   the request body.

## Decisions

### 1. RS256, verified against a published JWKS

The auth context signs with an RSA private key and publishes the public key at
`GET /.well-known/jwks.json`. The verifier **pins RS256** and never reads `alg`
from the token — accepting the token's own claim about how to check it is the
`alg: none` family of attacks, and the pin costs one line.

HS256 is defensible in a single process and would be less work today. It is
rejected on the strength of one property: with a symmetric secret, **anyone who
can verify can also mint**. [docs/00](../00-overview.md) targets 5–8 services,
and fraud, notifications and reports all need to *validate* tokens. Under HS256
each of them would hold forging power, so compromising the notifications
consumer — the least security-sensitive process in the system — would yield
admin tokens. Asymmetric keys make verification a strictly weaker capability
than issuance, which is the whole point of splitting them.

The cost is a keypair, a JWKS endpoint and `kid` handling: roughly an hour.
Paying it now is cheaper than migrating live tokens at extraction time, and it
is the answer this project wants to be able to give.

### 2. The private key comes from the environment, with no default

`BANKAPP_JWT_PRIVATE_KEY` holds a PKCS#8 PEM. `application.properties` carries
`${BANKAPP_JWT_PRIVATE_KEY}` with **no `:` fallback**, so a missing key fails
the context at startup rather than silently signing with a value that is in git.
This is NFR-08 applied literally: a dev default is acceptable only where using
it in production is obviously broken, and a signing key that works is never
obviously broken.

Dev keys are generated once by a documented `openssl` command and pasted into
`.env` — already gitignored, as are `*.pem` and `*.key`.

**Rejected: generating a keypair per boot.** It removes the configuration
burden and invalidates every token on restart, which makes local development
worse in exactly the way that teaches nothing, and it makes a JWKS endpoint
meaningless — consumers would cache a key that no longer exists.

Every token carries a `kid` header from the first commit, and JWKS serves a key
*set*, not a key, even while that set has one entry. The plumbing is nearly free
before there are tokens in the wild and is a migration afterwards. Rotation is
manual: publish both keys, switch the signing key, retire the old one after the
longest access-token TTL has elapsed.

### 3. Refresh tokens are opaque, hashed at rest, and rotated on use

A refresh token is **256 bits from `SecureRandom`, base64url** — not a JWT.
Making it a JWT would give it the one property it must not have: self-contained
verifiability, i.e. acceptance without a database lookup. The lookup *is* the
revocation check.

Stored in a `refresh_tokens` table as a **SHA-256 hash**, never plaintext, so a
database read does not yield usable credentials. Deliberately **not BCrypt** —
BCrypt's slowness defends low-entropy human passwords against offline guessing,
and a 256-bit random value has nothing to guess. Paying 100ms of key stretching
on every refresh buys nothing.

Row: `id`, `user_id`, `token_hash` (unique), `expires_at`, `revoked_at`,
`created_at`.

**Rotation on use.** Every `/refresh` issues a new refresh token and revokes the
one presented. A refresh token is therefore single-use, which turns theft into
something detectable: if a revoked token is presented, either the legitimate
client or the thief is replaying, and there is no way to tell which. The
response is to **revoke every refresh token for that user** and force a fresh
login. Losing one session to a false positive is the correct trade against
leaving a stolen long-lived credential live.

### 4. Claims and lifetimes

Access token: `sub` (user id), `roles`, `iss`, `aud`, `iat`, `exp`, `jti`.
**15 minutes.** Refresh token: 14 days, sliding via rotation.

A JWT is signed, not encrypted (JWS) — the payload is base64 and readable by
anyone holding the token. So: no email, no name, no account numbers, no
balances. `sub` is the user's UUID and the claims say what the holder may do,
never who they are in any human sense.

**Consequence to accept: roles are stale for up to 15 minutes.** An admin
demoted at 10:00 keeps admin authority until their access token expires.
Re-reading the user row on every request would close the window and would throw
away the statelessness that made a JWT worth choosing — at which point a session
cookie is the simpler design. The mitigation is the short TTL plus revoking the
refresh token, which stops renewal. This is a deliberate trade, not an oversight.

### 5. `role` is never a field the client can send

`POST /api/auth/register` is public, so every field it reads is
attacker-controlled. `RegisterRequest` carries `email`, `fullName`, `password`
and nothing else. The role is set inside `User.register(...)`, which can only
produce a CUSTOMER — not defaulted in the DTO, not defaulted in the handler,
where a later "just pass it through" refactor could reach it.

This is the same failure class as the `ownerId` problem in docs/07 —
client-supplied *privilege* rather than client-supplied *identity* — and `@Valid`
catches neither. Validation proves a value is well-formed, never that the caller
is entitled to it.

**The first ADMIN comes from the environment.** An `ApplicationRunner` reads
`BANKAPP_ADMIN_EMAIL` and `BANKAPP_ADMIN_PASSWORD` and creates an admin **only
if no admin row exists**; absent either variable it does nothing. Idempotent on
that check, so a restart cannot silently reset the password.

**Rejected: seeding an admin in a Flyway migration.** A BCrypt hash in git is a
credential in git (NFR-08), and migrations are immutable — the credential could
never be rotated, only superseded by another one also in git.

Subsequent admins are created by an existing admin through `POST
/api/admin/users`. That endpoint cannot create the first one, which is what the
bootstrap exists for.

### 6. Admins get their own surface, not a bypass inside the customer's

Authorization is declared in the filter chain, deny-by-default per NFR-11:
`/api/auth/**` and JWKS are `permitAll`, `/api/admin/**` is `hasRole('ADMIN')`,
everything else is `authenticated()`. `@PreAuthorize` repeats the role check at
the controller — not redundancy: one careless reordering of `requestMatchers`
and a path rule stops matching silently, and the method annotation is what
catches it. (It only fires through the proxy, so an internal call from a bean to
itself skips it.)

What this forbids is the tempting shape:

```java
if (!currentUser.isAdmin() && !account.ownerId().equals(currentUser.id())) { ... }
```

Three costs. Authorization scatters across every handler, so "what can an admin
reach?" stops being answerable by reading the security config. Admin actions
become indistinguishable from customer actions in the logs, so privileged access
cannot be audited. And every customer handler grows a branch whose *false* path
is the only one under test.

With separate paths, a customer handler has exactly one rule — does this
account's `ownerId` equal the token's `sub`? — with no branch, and admin read
paths are separate classes that can be audit-logged as a group.

**Roles are stored as one `varchar(20)` column with a check constraint**, not a
join table. Two mutually exclusive roles do not need a many-to-many. Switch
trigger: the first user who must hold two roles at once, at which point it
becomes `user_roles` and the token claim becomes a list — which it already is,
so only the read side changes.

### 7. Password hashing lives in the application layer

`BCryptPasswordEncoder` is a Spring bean, and hard rule 1 forbids
`org.springframework..` in `domain`. So `RegisterUserHandler` hashes the
plaintext and hands the domain a `PasswordHash` value object; `User` never sees
a plaintext password and cannot produce one.

This is the same shape as every other outbound dependency in the project: the
domain states what it needs as a type, the application layer supplies it. It
also means the domain test for registration needs no encoder and no Spring
context.

Plaintext is never logged, never in a `toString()`, and is bounded by a
`@Size(max = 72)` on the request — BCrypt silently truncates past 72 bytes, and
silent truncation of a credential is worse than a 400.

### 8. `users` belongs to the auth context; the existing FK stays, named

`V1__create_users_table.sql` predates the context boundaries and
`accounts.owner_id` carries `references users (id)`. Auth owns that table from
this slice on; accounts references a user **by id**, as ADR-001 requires.

The FK itself is a cross-context reference of exactly the kind ADR-003 decision
4 refused for `transfers`. It stays, and the inconsistency is recorded rather
than papered over: dropping it today would trade real referential integrity for
symmetry with a boundary that no extraction is currently approaching. Switch
trigger: the day auth owns a separate datastore, the constraint goes and the
check moves into the open-account use case, which is where transfers already
does it.

## Consequences

- The app fails to start without `BANKAPP_JWT_PRIVATE_KEY`. That is the intended
  behaviour and needs saying in `docs/10`, or the first missing-env failure
  reads as a bug.
- `V5` adds `password_hash` and `role` to `users`, and the row seeded by `V3`
  already exists — so a NOT NULL column cannot be added in one statement. Add
  nullable, backfill the dev user, then set NOT NULL, all inside `V5`. `V3` is
  immutable; editing it breaks the Flyway checksum.
- The dev user cannot simply be deleted: `accounts.owner_id` points at it, and
  every locally opened account with it.
- `ownerId` leaves `OpenAccountRequest` and comes from `sub`. That changes
  FR-ACC-01's error list — 409 unknown owner becomes unreachable — and every
  E2E test in slices 1–4 needs a token. The retrofit is the larger half of this
  slice; the three new endpoints are the smaller half.
- ADR-003 decision 7 can close: the idempotency-key constraint becomes
  `(userId, idempotencyKey)`, so two customers can pick the same key.
- Fraud, notifications and reports can validate tokens at extraction time
  without holding issuance power, and without a shared secret to distribute.
- A stolen access token is fully usable for up to 15 minutes and cannot be
  revoked. Only the refresh side is revocable. Shortening the access TTL further
  trades away the statelessness this design was chosen for.
- Rate limiting on `/login` and `/refresh` is **not** in this slice — NFR-14,
  slice 9. Until then credential stuffing is bounded only by BCrypt's cost
  factor, which bounds an attacker's throughput but not their attempts.
